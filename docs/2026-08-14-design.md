# react-progressive-picture — Design

Date: 2026-08-14
Status: Implemented as v0.1.0 (unpublished — see section 9)
Origin: extracted from `blitzleasing-portal` `src/components/common/Image/Image.tsx`

## 1. Context

`blitzleasing-portal` contains a 95-line React component that renders a responsive,
lazy-loaded `<picture>` with AVIF/WebP negotiation, an aspect-ratio box, and a blurred
low-quality placeholder that fades into the full image. It pairs with
`vite-imagetools` `?as=metadata`, which emits the exact source array the component wants.

The component is useful beyond this product, but it is not currently publishable: it
hardcodes a breakpoint, a blur radius, `object-fit`, `loading="lazy"`, and the
AVIF/WebP format pair, and it carries several defects that only matter once strangers
depend on it (section 4).

This document specifies extracting it into a standalone, public, MIT-licensed npm
package: **`react-progressive-picture`**.

### Motivation and its limits

There is no second consumer today. The package is being built to be given away, not to
serve a known internal need — so the usual "wait for the third use before extracting"
rule does not apply, but neither does any claim of urgency. The cost being accepted is a
public repo maintained indefinitely.

## 2. Decisions

Settled during brainstorming; recorded so they are not relitigated.

| Decision | Choice | Rejected alternative |
|---|---|---|
| Home | New standalone public GitHub repo | Subfolder of `blitzleasing-portal` — couples a public package's releases to a private product repo |
| npm identity | Unscoped `react-progressive-picture` (verified available 2026-08-13) | Personal scope; `@bikeleasing-service/*` GH Packages scope |
| Positioning | vite-imagetools-first, with config props | Ship as-is (unusable for others); fully generic image library (too large) |
| CSS delivery | Plain `.css` file export, themed by custom properties | Runtime `<style>` injection (CSP/SSR hazards); headless (removes the reason to use it) |
| Breakpoint | No `breakpoint` prop; CSS `@media` default at 768px | `matchMedia` + `useSyncExternalStore` — see 6.3 |
| Portal migration | Follow-up PR after v0.1.0 ships | Migrate in the same change |

### 2.1 Name vs positioning

The name describes the behaviour (progressive/blur-up loading) while the design is
optimised for vite-imagetools. These are reconciled by treating the input as a **plain
data contract** (section 3) that vite-imagetools happens to emit. The README leads with
the vite-imagetools quickstart but documents the hand-built array, so the name does not
promise toolchain independence the package fails to deliver.

## 3. Input contract

```ts
export interface ImageSource {
  src: string;
  width: number;
  height: number;
  format: string;
}
```

This is exactly what `vite-imagetools` returns for
`?w=30;480;768;1440;1920&format=avif;webp&as=metadata`. It is a structural type, not an
import from vite-imagetools — the package has no dependency on that plugin, and any
build tool or hand-written array satisfies it.

`height` is part of the contract because imagetools supplies it and future versions may
use it for intrinsic sizing. v0.1.0 does not read it.

## 4. Defects fixed during extraction

All seven exist in the current portal component and are in scope for v0.1.0.

**4.1 — `style` prop destroys the component.**
`Image.tsx:79-80` renders `<div style={containerStyle} {...props}>`. Because the spread
comes after `style`, any consumer passing `style` replaces the whole object, wiping
`--mobile-ratio`, `--desktop-ratio`, the placeholder `background-image`, and the blur.
Fix: merge — `style={{ ...containerStyle, ...style }}` — so consumer declarations win
per-property while the component's custom properties survive.

**4.2 — `sizes="100%"` is not valid HTML.**
The `sizes` attribute takes a source-size list whose values are CSS `<length>`s or
`auto`; percentages are not permitted. Browsers discard the invalid value and fall back
to `100vw`, which is why this has never been noticed. Fix: default `sizes` to `100vw`
and expose it as a prop.

**4.3 — A failed image stays blurred forever.**
Only the `load` event is observed. On `error` the `<img>` remains `opacity: 0` behind a
blurred placeholder, so neither the broken-image affordance nor the alt text ever
appears. Fix: treat `error` as terminal — set the loaded state so the blur clears and the
alt text surfaces.

**4.4 — `loading="lazy"` is hardcoded.**
The portal uses this component for its hero background, so its LCP candidate is
lazy-loaded. Fix: expose `loading` and `fetchPriority` props, defaulting to `'lazy'`
(correct for the general case) and letting hero usage opt into `eager` / `high`.

**4.5 — Formats hardcoded to AVIF and WebP.**
`getImagesByFormat('avif')` / `('webp')` are literal. Any other imagetools `format=`
query yields `<source srcSet="">` silently. Fix: derive format groups from the data
(section 5.3).

**4.6 — Placeholder assumes source ordering.**
`webpImages[0]` is the placeholder, correct only if imagetools emits ascending widths.
That ordering follows the query string, not a guarantee. Fix: select by `Math.min` on
`width`.

**4.7 — `alt` defaults to `''`.**
Defaulting to empty silently marks every image decorative, which is an accessibility
failure mode that a library should not make easy. Fix: `alt` is required; decorative
callers pass `alt=""` explicitly. The portal is such a caller and will be updated.

## 5. API

### 5.1 Props

```ts
import type { ComponentPropsWithoutRef, CSSProperties } from 'react';

export interface ProgressivePictureProps
  extends Omit<ComponentPropsWithoutRef<'div'>, 'children'> {
  /** Ordered image variants. Any format/width mix; grouped and sorted internally. */
  sources: ImageSource[];
  /** Required. Pass "" for decorative images. */
  alt: string;
  /** CSS aspect-ratio. A string applies at all widths; the object form switches at 768px. */
  ratio?: string | { mobile: string; desktop: string };
  /** Placeholder blur radius. Default '2rem'. */
  blur?: string;
  /** Default 'cover'. */
  objectFit?: CSSProperties['objectFit'];
  /** Default '100vw'. Must be a valid source-size list. */
  sizes?: string;
  /** Default 'lazy'. Use 'eager' for LCP images. */
  loading?: 'lazy' | 'eager';
  /** Maps to the img fetchpriority attribute. */
  fetchPriority?: 'high' | 'low' | 'auto';
  /** Override the placeholder URL, or false to disable blur-up entirely. */
  placeholder?: string | false;
  /** Escape hatch onto the underlying <img>. */
  imgProps?: ComponentPropsWithoutRef<'img'>;
}
```

Extending `ComponentPropsWithoutRef<'div'>` means `className`, `style`, `id`,
`data-*`, and ARIA attributes pass through to the container. `children` is omitted —
the container's contents are owned by the component.

### 5.2 Renames from the portal component

- `imageSources` → `sources`
- `alt` becomes required
- `ratio` additionally accepts a plain string; `'auto'` remains valid in both forms
  (the portal relies on `desktop: 'auto'`)

### 5.3 Format grouping and ordering

`<picture>` selects the **first** `<source>` the browser supports, so source order *is*
the preference order. Deriving that order from the input array would make output depend
on the order of `format=` in an imagetools query string — fragile and invisible.

Instead: group by `format`, then order groups by a fixed preference table —
`avif, webp, png, jpeg, jpg, gif` — with unrecognised formats appended in
first-appearance order. Within a group, sort ascending by `width`.

- One `<source>` per group, `srcSet` built as `` `${src} ${width}w` `` joined by `, `,
  carrying `type="image/<format>"` and the resolved `sizes`.
- The fallback `<img src>` is the **widest** entry of the **last** group — the most
  broadly compatible format available.
- The placeholder is the **narrowest** entry of the last group, applied as a CSS
  `background-image`. `<picture>` negotiation does not apply to a CSS background, so the
  most compatible format is the correct choice.

For the portal's `format=avif;webp`, this reproduces today's output exactly.

### 5.4 Edge cases

- `sources` empty → render `null`.
- A `placeholder` of `false` → no `background-image`, no blur, no shimmer; the image
  simply fades in.
- Explicit `placeholder` string → used verbatim, bypassing group selection (supports
  inline data-URI LQIP).

## 6. CSS

### 6.1 Delivery

A single stylesheet, imported once by the consumer:

```js
import 'react-progressive-picture/style.css';
```

The README leads with this line, because a forgotten stylesheet import is the most
common failure mode for this packaging style.

### 6.2 Class names

CSS Modules are dropped. Hashed class names cannot be targeted by consumers, which makes
overrides impossible without `!important` or wrapper selectors. The package ships stable
prefixed names: `.rpp-root`, `.rpp-picture`, `.rpp-img`, and the state class
`.rpp-loaded`.

### 6.3 Custom properties as the theming API

| Property | Default | Purpose |
|---|---|---|
| `--rpp-ratio` | `auto` | Aspect ratio below the breakpoint |
| `--rpp-ratio-desktop` | `auto` | Aspect ratio at/above the breakpoint |
| `--rpp-blur` | `2rem` | Placeholder blur radius |
| `--rpp-object-fit` | `cover` | Image fit |
| `--rpp-fade-duration` | `250ms` | Load-in transition |
| `--rpp-shimmer-color` | `rgb(255 255 255 / 0.1)` | Pulse overlay colour |
| `--rpp-shimmer-duration` | `2.5s` | Pulse period |

**Breakpoint decision.** CSS custom properties cannot be used in `@media` conditions, so
a `breakpoint` prop cannot be implemented in CSS alone. The stylesheet therefore ships a
fixed `@media screen and (min-width: 768px)` that swaps `--rpp-ratio` for
`--rpp-ratio-desktop`, and consumers needing a different breakpoint override the custom
property from their own media query:

```css
.my-hero { --rpp-ratio: 16 / 9; }
@media (min-width: 900px) { .my-hero { --rpp-ratio: 21 / 9; } }
```

The rejected alternative was a `breakpoint` prop backed by `matchMedia` and
`useSyncExternalStore`, removing `@media` from the stylesheet. It yields a more honest
prop but adds a subscription plus an SSR fallback render for something one CSS rule
already solves. Revisit only if the CSS override proves insufficient in practice.

## 7. Build and packaging

Vite library mode with `vite-plugin-dts`. Entry `src/index.ts`.

- Output: ESM only — `dist/index.js`, `dist/index.d.ts`, `dist/style.css`
- `peerDependencies`: `react >= 18`. No `react-dom` — the component imports nothing from
  it. No runtime dependencies; `classnames` is replaced by a `filter(Boolean).join(' ')`
  expression.
- `sideEffects: ["*.css"]` so bundlers may tree-shake the JS but never drop the stylesheet
- `files: ["dist"]`

```json
{
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./style.css": "./dist/style.css"
  }
}
```

Public exports: `ProgressivePicture` (named), and the types `ProgressivePictureProps`
and `ImageSource`.

## 8. Testing

Vitest + happy-dom + Testing Library, mirroring the portal's stack.

Cases:

1. One `<source>` per format group, `srcSet` entries formatted `src widthw`
2. Group order follows the preference table; unknown formats appended
3. Widths sorted ascending within a group
4. Fallback `<img src>` is the widest entry of the last group
5. Placeholder is the narrowest entry of the last group
6. `placeholder={false}` emits no `background-image` and no blur
7. Explicit `placeholder` string is used verbatim
8. Loaded state set when the image is already complete on mount
9. Loaded state set on the `load` event
10. Loaded state set on the `error` event (defect 4.3)
11. A consumer `style` prop merges rather than replacing the custom properties (defect 4.1)
12. `className` merges with `.rpp-root`
13. `ratio` string form and object form both resolve; `'auto'` accepted
14. `loading` / `fetchPriority` / `sizes` reach the `<img>`
15. `sources={[]}` renders nothing

Known wrinkle (corrected during implementation): happy-dom does populate
`HTMLImageElement.prototype.complete`, and never having fetched anything, it reports
`true` for every image. So the wrinkle is the opposite of what was assumed — case 8 passes
for free, while cases 9 and 10 need `complete` pinned to `false` before mount or the
component is already in its loaded state. Both directions go through one `withComplete`
helper that restores the original descriptor.

## 9. Release

**First publish is manual.** npm trusted publishing (OIDC) can only be configured for a
package that already exists, so v0.1.0 goes out by hand:

```
npm publish --access public --provenance
```

Afterwards, trusted publishing is enabled in the npmjs.com package settings and releases
run from a tag-triggered GitHub Actions workflow — no long-lived `NPM_TOKEN` secret.

CI on pull requests: lint → typecheck → test → build.

Versions are bumped by hand with `npm version`. Changesets and semantic-release are not
warranted for a single-component package; add them if release friction becomes real.
